# 그림자 엔진 — 구현 가이드

> 이 문서는 **"그림자 코드가 실제로 어떻게 도는가"** 를 설명하는 구현 가이드다.
> - 무엇을/왜(재미) → [기획서.md](../기획서.md)
> - 어떻게 만들 계획인가 → [개발기획서.md](../개발기획서.md) §2.1
> - 왜 이 구조인가(의사결정) → [아키텍처_결정_기록.md](../아키텍처_결정_기록.md) §2.1
> - **이 코드가 도는 원리(여기)** ← 큰 그림. 줄단위 정밀 레퍼런스는 각 파일의 XML 주석.

그림자 모델 = **캐릭터(캐스터)가 태양을 가려 만든 캐스트 섀도우**를, 차폐물(플랫폼)에 막혀
잘리도록 계산한다. 계산 알고리즘은 **Rotational Sweep**(redblobgames visibility)을
캐스터 호에 맞춰 적용한다.

> (직전 임시 구현은 sweep이 아니라 brute-force 광선 샘플링이었고, 정통 끝점 sweep으로 교정함 — [변경 이력](#변경-이력))

## 1. 전체 흐름

매 프레임 아래 파이프라인이 돈다.

```
SunLightSource ──ISunPosition──┐
OccluderField ─IOccluderSource─┐
                               ├─▶ ShadowSystem ─▶ IShadowEngine ─▶ ShadowPolygon ─▶ IShadowCaster(ShadowCaster) 렌더
ShadowConfig ─IShadowConfig────┘
```

| 역할 | 타입 | 위치 |
|------|------|------|
| 광원 위치 | `ISunPosition` ← `SunLightSource` | [Core](../Assets/Scripts/Core/ISunPosition.cs) / [Sun](../Assets/Scripts/Domains/Sun/SunLightSource.cs) |
| 차폐물 기하 | `IOccluderSource` ← `OccluderField`/`Occluder` | [Core](../Assets/Scripts/Core/IOccluderSource.cs) / [Map](../Assets/Scripts/Domains/Map/OccluderField.cs) |
| 매 프레임 구동 | `ShadowSystem` (`ITickable`) | [Shadow](../Assets/Scripts/Domains/Shadow/ShadowSystem.cs) |
| 그림자 계산 | `IShadowEngine` ← `RotationalSweepShadowEngine` | [Core](../Assets/Scripts/Core/IShadowEngine.cs) / [Shadow](../Assets/Scripts/Domains/Shadow/RotationalSweepShadowEngine.cs) |
| 캐스터 + 표시 | `IShadowCaster` ← `ShadowCaster` | [Core](../Assets/Scripts/Core/IShadowCaster.cs) / [Shadow](../Assets/Scripts/Domains/Shadow/ShadowCaster.cs) |
| 데이터 | `CasterShape`, `ShadowPolygon`, `Segment` | [Core](../Assets/Scripts/Core/) |
| 튜닝값 | `IShadowConfig` ← `ShadowConfig`(SO) | [Shadow](../Assets/Scripts/Domains/Shadow/ShadowConfig.cs) |

> 도메인 간 직접 참조는 없다. Sun/Map ↔ Shadow 연결은 전부 `Core`의 인터페이스를 통하고,
> 실제 배선은 `App`의 [RootLifetimeScope](../Assets/Scripts/App/RootLifetimeScope.cs)에서 한다.

## 2. 1단계 — `ShadowSystem.Tick()` (구동)

입력(태양·차폐물)을 모아 엔진을 호출하고, 결과를 캐스터에 넘긴다.

```csharp
var poly = _engine.ComputeShadow(
    _sun.WorldPosition,        // 광원 위치
    _caster.Shape,             // 박스: 중심 + 크기 + ownerId
    _occluders.Segments,       // 차폐물 선분들
    _config.MaxShadowLength);  // 차폐물 못 만났을 때 최대 길이
_caster.Render(poly);
```

`ITickable`로 등록돼 **타이밍을 컨테이너가 통제**한다([개발기획서.md](../개발기획서.md) §4.7).

> ⏱️ 지금은 시각용이라 `Tick`(매 프레임). 밟기 판정에 쓰이면 결정성을 위해 `FixedTick`으로 옮긴다.

## 3. 2단계 — `RotationalSweepShadowEngine` (핵심 계산)

### 핵심 통찰 (redblobgames)

> **그림자(가시 경계)의 꼭짓점은 오직 차폐물의 "끝점"에서만 생긴다.**

끝점과 끝점 사이 구간에서는 "가장 가까운 벽"이 안 바뀌므로 경계가 직선이다. 그래서 광선을
무한히/촘촘히 쏠 필요가 없고, **끝점 방향으로만** 쏘면 정확한 폴리곤이 나온다. 이게 sweep의
알맹이고, 비용은 `O(n log n)`(정렬 지배)이다.

### (a) 캐스터 호 구하기
태양에서 본 박스 네 모서리의 **부호 각도**(중심 방향 기준)를 재서, 가장 왼쪽/오른쪽 모서리
`a`, `b`(실루엣 극단)와 그 각도 범위 `[θ_a, θ_b]`를 얻는다. 이 호 안에서만 sweep 한다.
`a`,`b`를 잇는 chord가 그림자의 **near edge**(캐스터 쪽 변)다.

```
        ☀ light
       ╱   ╲          a, b = 태양에서 본 박스의 양 극단 모서리
      ╱ box ╲          호 [θ_a, θ_b] = 캐스터가 가리는 각도 범위
     a────────b
```

### (b) 끝점 정렬
플랫폼 차폐물(**캐스터 자신은 제외**) 선분들의 끝점 중 호 `[θ_a, θ_b]` 안에 드는 것을
**각도순 정렬**한다. 각 끝점은 자기 벽의 **begin**(sweep이 먼저 만나는 쪽) / **end** 로 표시.

### (c) sweep — open 집합 + nearest 추적
호를 한 번 훑으며, 광원에서 가장 가까운 벽을 추적한다. nearest가 바뀌는 끝점에서만 far edge
꼭짓점을 찍는다.

```
open = []          # sweep 광선이 지금 가로지르는 벽들
far  = []          # far edge(그림자 끝선) 꼭짓점

각 endpoint(각도 θ)를 각도순으로 돌면서:
    oldNearest = open 중 광원에 가장 가까운 벽
    if begin: open.add(그 벽)
    if end:   open.remove(그 벽)
    newNearest = open 중 가장 가까운 벽
    if oldNearest != newNearest:           # ← 여기서 경계가 꺾인다
        far.add( 광선(θ) ∩ oldNearest )    # 옛 벽에서 떨어지는 점
        far.add( 광선(θ) ∩ newNearest )    # 새 벽으로 옮겨가는 점
```

- **open 집합**: 현재 각도의 광선이 관통 중인 벽 목록. 끝점을 지나며 벽이 들어오고(begin) 나간다(end).
- **nearest**: open 중 광원에 가장 가까운 벽 = 그 방향에서 그림자가 떨어지는 표면. (그 뒤는 가려짐)
- **꼭짓점 emit 조건**: nearest가 바뀔 때만. 예) 가까운 벽이 끝나(end) 뒤의 먼 벽이 드러나면 →
  두 벽 위의 교점을 꼭짓점으로 찍어 far edge가 그 끝점에서 꺾이게 한다.
- **벽이 없는 방향**(open 비어있음): 그림자가 무한히 가지 않게 `maxLength`로 잘라 far 점을 둔다.

### (d) 폴리곤 조립
```
near edge: a → b                 (실루엣 chord)
far edge : b쪽 → … → a쪽          (sweep이 emit한 꼭짓점들)
ShadowPolygon = near + 역순 far
```

→ 차폐물 끝점에서 정확히 꺾이는 그림자. 플랫폼에 막히면 그 위에서 끝나 **안전지대**가 성립한다.

> robust 처리 메모: nearest 비교는 거리 계산보다 "한 벽이 다른 벽보다 앞에 있나" 판정이 안정적이다.
> 끝점 각도에서 광선이 끝점 위를 정확히 지날 때 누락을 막으려면 각도 ±ε 처리/정렬 타이브레이크가 필요하다.
> (구현 시 이 부분이 가장 버그 나기 쉬움.)

## 4. 3단계 — `ShadowCaster.Render` (표시)

폴리곤을 메쉬로 그린다. 그림자는 차폐물에 잘려 **오목(concave)** 해질 수 있어,
단순 fan이 아니라 **ear-clipping 삼각분할**(오목 다각형 안전) + 양면으로 그린다.

- 캐스터 transform이 world-space 폴리곤을 다시 밀지 않도록, 메쉬는 **월드 원점의 별도 오브젝트**에 올린다.

## 5. 여러 캐스터로 확장하기

지금은 캐스터 1개지만 구조가 N-ready다. 이유:

- **엔진은 캐스터 수를 모른다** (호출당 1개). 캐스터를 늘려도 엔진/계약/렌더는 안 바뀐다.
- 캐스터는 `IShadowCaster`로 추상화돼 있어 **꽂을 수 있다(pluggable)**.

확장 시 바뀌는 건 `ShadowSystem`이 **단일 캐스터 대신 목록을 루프**하는 국소 변경뿐:

```csharp
foreach (var c in _casters)
{
    var poly = _engine.ComputeShadow(sun, c.Shape, occluders, maxLength);
    c.Render(poly);
}
```

- 새 캐릭터/물체 = `IShadowCaster` 구현 + 등록. 환경 오브젝트는 `ownerId = -1`(중립).
- 런타임 스폰이 필요해지면 작은 레지스트리(등록/해제)를 둔다 — 그때 가서 (과설계 금지).

> **캐스터 vs 차폐물 구분**: 캐스터는 그림자를 *만드는* 것(실루엣 제공), 차폐물은 그림자를 *막는/받는* 것(선분 제공).
> 플랫폼은 차폐물이지 캐스터가 아니다(태양 뒷배경 설정 — 플랫폼 자체 그림자 최소화).

## 6. 설계 포인트

- **`ShadowPolygon`(+`OwnerId`) 하나가 단일 진실**: 렌더 + (나중에) 밟기 판정이 같은 폴리곤을 소비 → "보이는 것 = 판정되는 것" ([개발기획서.md](../개발기획서.md) §2.2).
- **엔진은 `IShadowEngine` 뒤에 숨음**: 구현 교체 시 소비자 불변. (투영 → sweep 교체가 그 증명)
- **광원 출처는 `ISunPosition` 뒤에 숨음**: 손으로 옮기는 `SunLightSource` → 나중에 궤도 `SunOrbitService`. 그림자 코드 무관.

---

## 7. 현재 한계 (의도된 단순화)

- **캐스터 = 박스 1종**, near edge는 실루엣 chord로 근사(박스 뒷면 형상 무시) — 시각상 충분.
- **자기 그림자/상호 차폐 없음**: 차폐물 목록에 캐스터 자신·다른 캐스터는 안 들어감.
- **무한 맵 wrap 미적용**: 경계 넘는 그림자 처리는 후순위([개발기획서.md](../개발기획서.md) §2.4).

## 변경 이력

> 폐기된 구현은 지우되 "무엇을 왜 버렸나"는 남긴다(git이 코드 자체는 보관).

- **투영(Projection) 모델 → 캐스트 섀도우 모델** (Stage 1)
  - *이전*: `ProjectionShadowEngine` — 박스 윗변을 평평한 `groundY` 직선 하나에 투영한 사다리꼴. 차폐물 개념 없음.
  - *폐기 이유*: 평평한 바닥 직선만 지원해 **플랫폼에 막혀 잘리는 그림자(안전지대)** 를 표현할 수 없었다. 또 `groundY`가 실제 맵 기하와 분리돼 있었다.
  - *대체*: 차폐물(`IOccluderSource`)에 그림자가 막혀 끝나게. `groundY` 제거(바닥 = 넓은 차폐물 하나). `IShadowEngine` 계약이 `(light, caster, occluders, maxLength)`로 바뀌고 소비자는 거의 그대로.

- **brute-force 광선 샘플링(임시) → 정통 끝점 sweep** (Stage 1, 교정)
  - *이전(임시)*: 호를 64등분해 광선 64개를 쏘고 nearest를 찾던 방식. sweep이 아니라 무작정 ray marching — 부정확(계단 근사)하고 "Rotational Sweep"이라는 이름값을 못 함.
  - *폐기 이유*: redblobgames의 핵심(끝점만 처리 + open/nearest 추적)을 빠뜨린 잘못된 단순화였다.
  - *대체*: §3 설계대로 끝점 각도 정렬 + open 집합 + nearest 변화 시에만 꼭짓점 emit (정확, `O(n log n)`).
