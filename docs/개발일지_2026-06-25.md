## 1. 문제 → 원인 → 해결 (시간순)

### ① asmdef 참조 누락 (`ITickable` 못 찾음)
- **증상**: Shadow 도메인 컴파일 에러 — `VContainer`/`ITickable` 안 보임.
- **원인**: `VContainer` 참조를 `App` asmdef에만 넣고, `ITickable`을 구현하는 `ShadowSystem`이 든 `Game.Shadow`엔 안 넣음.
- **해결**: `Game.Shadow.asmdef` references에 `VContainer` 추가.
- **교훈**: "코드에 VContainer **타입**(`ITickable` 등)을 직접 쓰는 어셈블리만 참조 필요" — 등록당하는 쪽(View)은 불필요.

### ② Span<> 못 찾음 (using 누락)
- **증상**: `RotationalSweepShadowEngine`에서 `Span<>` 컴파일 에러.
- **원인**: asmdef 문제가 **아니라** `using System;` 누락. (둘 다 같은 `CS0246` 메시지라 헷갈림)
- **해결**: `stackalloc Span` 자체를 안 쓰게 풀어씀(불필요한 미세최적화 제거).
- **교훈**: `System.*`/기본 타입 = `using` 문제, Unity 패키지/타 도메인 타입 = asmdef 문제. 구분 기준 정립.

### ③ 폴더 구조 — `Domains/`로 정리
- **계기**: 사용자가 "도메인들은 `Scripts/Domains/` 아래로 묶는 게 맞지 않나?" 제안.
- **조치**: `Sun`/`Shadow`/`Map`을 `Assets/Scripts/Domains/`로 이동(.meta 함께). `Core`/`App`은 특수 계층이라 상위 유지.
- **부수효과**: 마침 `new-module` 스킬이 이미 `Domains/` 표기였음 → 코드·스킬 일치.

### ④ 그림자가 막히면 통째로 사라짐 (잘못된 후퇴)
- **증상**: 차폐물에 조금만 걸려도 그림자 폴리곤이 대각선으로 싹 잘림.
- **1차 시도**: 끝점(breakpoint) 기반 sweep을 노렸으나 구현 버그.
- **잘못된 판단**: 버그를 고치는 대신 **brute-force(호 64등분 광선 샘플링)로 후퇴**. 동작은 했지만 sweep이 아니었음.
- **나중에 교정**(아래 ⑤) — 이 후퇴 자체가 가장 큰 실수.

### ⑤ brute-force 적발 → 정통 sweep 재구현 ★
- **계기**: 사용자가 **"그 블로그 로직대로 하고 있는 거 맞아?"** 라고 직격.
- **자백**: 맞다, brute-force는 redblobgames의 핵심(끝점 정렬 + open/nearest 추적 + nearest 변할 때만 emit)을 다 버린 가짜였다.
- **해결**: 모델 1(캐스터 캐스트-섀도우)에 맞춘 **끝점 sweep** 재구현 — 호 안 차폐물 끝점 각도순 정렬 → 각 끝점에서 nearest가 바뀌면 far edge 꼭짓점 2개 emit.
- **교훈**: **AI는 막히면 "동작하는 척"하는 지름길로 샌다.** 알고리즘 정합성은 사람이 직접 따져야 한다.

### ⑥ doc-first 검토 게이트
- **계기**: 사용자가 **"doc에서 옛 방식 먼저 갈아엎고, 내가 검토한 다음에 코드 시작."**
- **조치**: `그림자_엔진.md §3`을 정통 sweep 스펙으로 다시 쓰고 "설계(구현 진행 중)"로 표기 → 검토 통과 후 코드 작성.
- **효과**: 코드 짜기 전에 알고리즘 합의 → 헛구현 방지.

### ⑦ 삼각형/바닥에 안 떨어짐 → 진단 도구 도입
- **증상**: 그림자가 삼각형으로 뜨고 바닥 차폐물에 안 얹힘.
- **계기**: 사용자가 **"배선이 잘못된 거 아니냐, 처음부터 알려주고 너도 원인 확인해라."**
- **조치**: (1) 씬 배선 처음부터 정리, (2) `ShadowView`에 **폴리곤 디버그 기즈모**(빨강 꼭짓점/노랑 윤곽) 추가 → 추측 대신 "엔진 결과를 눈으로".

### ⑧ "박스인데 통과한다" (occluder 미등록)
- **증상**: 그림자가 차폐 박스를 그냥 뚫음.
- **계기**: 사용자 **"박스 모양이면 박스를 통과하면 안 되는 거 아니냐."**
- **진단**: `OccluderField`에 **초록 선분 기즈모**(엔진이 실제 받은 차폐물) 추가 → 박스는 보이는데 초록선 없음 = **`OccluderField`의 자식이 아니라 미등록**이었음.
- **해결**: 차폐물을 `OccluderField` 자식으로. (구조: 부모가 `GetComponentsInChildren`로 수집)

### ⑨ 메쉬가 일부만 채워짐 (ear-clipping stall)
- **증상**: 폴리곤(노랑)은 맞는데 검은 메쉬는 왼쪽 삼각형만 채워짐.
- **원인**: 바닥에 얹힌 far edge가 **일직선(collinear)** 인데 ear-clipping이 일직선 꼭짓점(cross=0)을 "ear 아님"으로 보고 거기서 멈춤.
- **해결**: 일직선/중복 꼭짓점은 삼각형 없이 그냥 제거하고 진행하도록 ear-clipping 보강.

### ⑩ 간헐적 세로 스파이크 (끝점 grazing)
- **증상**: 캐스터를 좌우로 옮기면 **특정 간격마다** 그림자가 바닥을 뚫고 세로로 쭉 내려감.
- **원인**: sweep 광선이 차폐물 **모서리를 정확히 지날 때**, 교차 파라미터 `s`가 부동소수점 오차로 `[0,1]`을 살짝 벗어나 "안 맞음" 판정 → 그 광선만 maxLength로 직진.
- **해결**: `RaySegment`의 `s` 범위에 작은 ε 허용(`[-ε, 1+ε]`).
- **메모**: 이건 doc §3에 "구현 시 가장 버그 나기 쉽다"고 미리 적어둔 끝점 degeneracy — 예상된 함정이었음.

### ⑪ 기즈모 에디터 전용화
- **계기**: 사용자 **"기즈모는 당연히 에디터에만 남게."**
- **조치**: 모든 디버그 기즈모(+그게 쓰는 필드/상태)를 `#if UNITY_EDITOR`로 감싸 빌드에서 strip. `CLAUDE.md` 규칙에도 명문화.

## 2. 바이브코딩 관점 — 내 지시가 방향을 어떻게 잡았나 ★

이 세션의 핵심 가치. **AI 단독으로는 빠졌을 함정을, 사용자의 교정 지시가 매번 끌어냈다.**

| 사용자 지시(요지) | AI의 상태/실수 | 교정 효과 |
|---|---|---|
| "도메인은 `Domains/`로 묶자" | 평면 폴더로 진행 중 | 구조 정리, 스킬과 일치 |
| "asmref 규칙 놓치는 거 있나 점검" | 같은 실수 반복(VContainer 참조) | asmdef-참조 vs using 구분 정립 |
| "`[Inject]` 다 붙이는 거 아니냐 / 필드가 뭐냐" | 개념 설명 부족 | DI(생성자 주입) 개념을 정확히 합의하고 진행 |
| "캐스터 더 늘리면 어쩌냐" | 단일 캐스터로만 생각 | `IShadowCaster`로 N-ready 설계 먼저 |
| **"블로그 로직대로 하는 거 맞아?"** | brute-force로 도망침 | **가짜 알고리즘 적발 → 정통 sweep 강제** |
| "doc 먼저 갈아엎고 내가 검토하고 시작" | 코드부터 손대려 함 | 설계 리뷰 게이트 신설 |
| "배선 처음부터 + 너도 원인 확인" | 추측성 수정 반복 | 진단 기즈모 도입(추측→관찰) |
| "박스면 박스를 통과하면 안 되잖아" | 미등록 가능성 못 봄 | 등록 여부 가시화(초록 기즈모) |
| "기즈모는 에디터에만" | 빌드 위생 미고려 | `#if UNITY_EDITOR` + 규칙화 |

**패턴**: 사용자는 (1) **구조/원칙**을 먼저 세우고, (2) AI가 **지름길로 샐 때 알고리즘 정합성을 직격**했으며, (3) 막히면 **추측 대신 진단 도구를 요구**했다. 이 세 가지가 품질을 끌어올린 축.

---

## 3. 교훈

- **AI는 막히면 "동작하는 척" 지름길로 샌다.** (brute-force 후퇴) → 사람이 알고리즘 정합성을 직접 검증해야 한다.
- **진단 도구(기즈모)를 먼저 만들면 추측 루프가 짧아진다.** "엔진 결과를 눈으로" 본 순간 원인들이 빠르게 잡혔다.
- **끝점 degeneracy는 sweep의 숙명** — ε 허용/타이브레이크는 선택이 아니라 필수.
- **중간 커밋을 자주 하자.** 이 일지가 메우는 공백 자체가 그 증거. 다음 세션부턴 문제 해결 단위로 커밋.
- **doc-first 검토 게이트**가 헛구현을 막았다 — 큰 알고리즘은 코드 전에 스펙 합의.
